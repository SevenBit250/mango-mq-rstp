# 720p@60fps 是怎么做到的

## 1. 链路

```
OV5640 (DVP 8-bit YUV422)
   │  PCLK / HREF / VSYNC / D[7:0]
   ▼
sunxi VIN: CSI → (ISP bypass) → scaler → vinc0
   │  NV21M，两个平面
   ▼
vencoder 的 ion 输入缓冲（VIN 直接 DMA 写进来，用户态不拷贝）
   │
   ▼
D1s VE 硬件 JPEG 编码（VencJpeg，码率模式）
   │
   ▼
RTP/JPEG (RFC 2435) → WiFi
```

驱动这边要注意的点：

- `sensor0_isp_used=0`，ISP 旁路，格式转换由 scaler 做。
- `isp0` 没有独立中断，和 CSI 共用 plic 116。
- dtsi 里 ISP/scaler 的 `device_id` 是 0xfe/0xff，但驱动拿它当 `glb_isp[]` 下标用，必须改成 0/1。
- sensor0 的 reset/pwdn 在 v1.5 板子上没接到 GPIO（PE8/PE9 实际是 DVP 的 Y6/Y7），DTS 里删掉这两个属性。

## 2. 关键约束：DVP 像素时钟

OV5640 手册表 8-5（AC 特性，p.168）：

- DVP 并行口 PCLK：典型 **48MHz**，最大 96MHz
- 脚注：96MHz 只用于 RAW@15fps 或 YUV@7.5fps；更高 YUV 速率官方建议改用 MIPI 双 lane

表 2-1（p.22）里 720p60 那列的 96/192MHz 是像素时钟/MIPI 时钟，不是 DVP 的可靠工作点。

D1s 这边（F133 UM p.21）并行 CSI 标称最大像素时钟 148.5MHz（DDR 模式），设备树 `csi_top = 336MHz`。84MHz 时正好 4 倍，余量为零。

第一次做 60fps 时用的是标准时序：

```
HTS 1892 × VTS 740 × 60fps = 84MHz
```

帧率计数是准的（60.01fps），但画面右侧整行丢数据：每行只写进 1048–1280 列，最右 77–90 列 Y=0，转 RGB 后是饱和绿色。

在流运行中用 i2c 改传感器寄存器（`tools/i2c_wr.c`），逐档验证：

| 像素时钟 | 寄存器 | 画面 |
|---|---|---|
| 84MHz | 0x3036=0x54 | 右侧截断 |
| 80MHz | 0x3036=0x50 | 干净 |
| 78MHz | 0x3036=0x4E | 干净 |
| 72MHz | 0x3036=0x48 | 干净 |
| 42MHz | 0x3035=0x21 | 干净 |

也就是说瓶颈是瞬时 PCLK 频率，大约 80MHz 以上不可靠，不是平均带宽。

## 3. 最终时序

保持 60fps，把 HTS 缩短、PCLK 降低，行时间基本不变：

```
原来（30fps）: HTS 1750 × VTS 800 × 42MHz
最终（60fps）: HTS 1750 × VTS 740 × 78MHz
               fps = 78e6 / (1750 × 740) = 60.23
```

寄存器改动：

| 寄存器 | 原值 | 新值 | 含义 |
|---|---|---|---|
| 0x3035 | 0x21 | 0x11 | 系统时钟分频，1 |
| 0x3036 | 0x54 | 0x4E | PLL 倍频，78MHz |
| 0x380c/0d | 0x0764 | 0x06d6 | HTS 1750 |
| 0x380e/0f | 0x0320 | 0x02e4 | VTS 740 |

有效像素还是 1280×720，行消隐从 612 个时钟降到 470 个。

实测：

```
$ v4l2_fps 1280 720 3
frames=180  duration=3003ms  fps=60.23  (first frame 31ms)

裸帧检查：dark cols 0，每行 1272–1280 有效像素
```

## 4. 零拷贝

VIN 用 mmap 拿到的缓冲是 uncached 的，往编码器缓冲里 memcpy 一帧 1.4MB 要 **40ms**，直接把 60fps 吃掉了（当时实测只有 13fps）。

改成：申请 3 个 vencoder 的 ion 输入缓冲，通过 V4L2 **NV21M 双平面 USERPTR** 直接交给 VIN 写。采集线程拿到 DQBUF 后，用同一组 Y/C 指针调 `AddOneInputBuffer` 编码，不再拷贝。

编码本身是 4ms 左右：

```
us/frame: add 12 encode 3977 ret 5 get 9 publish 124
```

## 5. 编码和 RTP

- VENC_CODEC_JPEG，码率模式（`VENC_IndexParamJpegEncMode=1`），按 kbps 均摊每帧大小。
- 编码输出是标准 JPEG：4:2:0，标准的 IJG Huffman 表（这点很重要，见下）。
- RTP 用 PT 26 / RFC 2435。ffmpeg 的实现里几个地方和 RFC 文本不完全一样，按它的来：
  - 分片偏移是**字节数**，不是 8 字节单位
  - 第一片带 8 字节 JPEG 头 + 4 字节表头 + 2 张 8-bit 量化表（qtable_len=128）
  - 后续分片只有 8 字节头
  - 负载里只放**扫描数据**（SOS 之后、EOI 之前）；SOF/DHT/SOS 由接收端自己拼
  - type=1 表示 4:2:0（ffmpeg 的约定）
- 接收端拼回 JPEG 时用标准 Huffman 表，和编码器输出的一致，所以 ffmpeg/OpenCV/VLC 能直接解。

发送放在单独线程，采集和发送解耦。8189FS 每个 UDP 包大约 1ms，720p60 每帧约 18 个包：

| 码率 | 帧大小 | 每帧包数 | 理论帧率 |
|---|---|---|---|
| 10Mbps | ~25KB | ~18 | 60 |
| 16Mbps | ~33KB | ~24 | ~40 |

所以默认 10Mbps，画质偏软但帧率稳。

## 6. 内存

- `cma=8M`（env.cfg）。CMA 在 VIN 这条路上用得很少，留太多反而挤占常规内存池。
- 进程内存：3 个编码输入帧约 4.2MB，编码器内部约 3MB，运行中 MemAvailable 16–20MB。
- `oom_score_adj=500`，内存紧张时内核先杀推流进程，不杀 dropbear。

## 7. 复现和验证

1. 按 `patches/README.md` 应用补丁，编译镜像并烧录。
2. 板子上确认模块和相机：

```sh
lsmod | grep -E 'vin_io|ov5640|vin_v4l2'
v4l2_fps 1280 720 3        # 期望 ~60fps
```

3. 抓一帧看右边缘是否完整：

```sh
capdump 1280 720 NV21      # 生成 /tmp/capdump.yuv
```

4. 跑推流并拉流：

```sh
mq_rtsp 10000 90 8554 1280 720
python tools/rtsp_recv.py rtsp://<板子IP>:8554/stream --secs 10
```

## 8. 编译 mq_rtsp

在 Tina SDK 的容器/环境里，用目标工具链链接 tina_multimedia 提供的编码器库：

```sh
$CC -O2 -g -o mq_rtsp mq_rtsp.c   -I$STAGING/usr/include/allwinner/include   -I$STAGING/usr/include/allwinner   -L$STAGING/usr/lib   -Wl,--dynamic-linker=/lib/ld-2.29.so   -lvencoder -lvenc_base -lvenc_common -lvenc_jpeg   -lvenc_h264 -lvenc_h265 -lcdc_base -lVE -lMemAdapter   -lpthread -ldl -lm
```

运行时要能加载 `libvencoder.so`、`libvenc_jpeg.so` 等（`LD_LIBRARY_PATH` 指过去，或者装进 `/usr/lib`）。`--dynamic-linker` 是因为板子 rootfs 里 `/lib64xthead/lp64d/ld-2.29.so` 缺失，直接用 `/lib/ld-2.29.so`。

## 9. 还没做的

- MIPI 接口没引出，只能用 DVP。
- 1080p/5MP 在 64MB 板上会 OOM。
- 推流目前是单客户端、UDP，没有做 RTCP 和 TCP interleaved。
